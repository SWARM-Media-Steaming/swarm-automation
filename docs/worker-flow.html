1. The big picture

A scheduler starts one worker run per repository on an interval. A run does at most one unit of work (one issue, or one resumed checkpoint), then exits with a code that tells the scheduler what happened.

Exit codeMeaningScheduler treats it as
0Nothing to do right nowidle
10ISSUE_COMPLETED_EXIT_CODE: delivered, answered, or asked for inputprogress
11QUOTA_PAUSED_EXIT_CODE: provider usage ran out; session savedprogress
12PROVIDER_UNAVAILABLE_EXIT_CODE: no enabled provider has its minimum remaining usageidle
13ADVERSARIAL_EPOCH_YIELD_EXIT_CODE: a strict stage renewed 3 epochs in this process; the checkpoint resumes next passprogress
14AUTOMATION_FAILED_EXIT_CODE: the issue is held after a repeated or deliberate failureidle
15RETRY_LATER_EXIT_CODE: a self-recovering condition (GitHub hiccup, rejected tester answer); logged quietlyidle

3. Starting work and the implementation pass

Notes

  • Question issues never change the repository and never enter the adversarial loop. Pre-flight grading and routing still run.
  • Only the worker writes VERSION (see .claude/rules/versioning.md).
  • Routing never overrides a manual model selection, and a started session is never re-routed to a different model unless its model was retired.

4. The adversarial pipeline

The stages are independent switches. Each runs its own loop to completion before the next starts, then delivery happens once.

Rules that hold for both stages (they share adversarial_core.py):

  • Fresh context. Every tester or reviewer starts a new session. It sees the issue, trusted amendments, the current diff, repository conventions and the failed approaches so far. It never sees the implementer's transcript or reasoning. It is also told which out-of-scope findings are already tracked.
  • Ownership. The fixer changes product code only. It cannot change, disable or retire anything under tests/adversarial/; the worker restores such edits and turns them into a dispute. UAT owns tests/adversarial/; cybersecurity owns tests/adversarial/security/. Neither may edit the other's suites.
  • Tester floor. A tester never runs below the scored STANDARD-task model at medium effort, and never weaker than the first assessment's tester.
  • Provider choice. Capacity is checked for every phase. Another provider is preferred for testing, and the dynamic router is reused when enabled.

5. Inside one adversarial stage: rounds and epochs

Round 0 is the independent assessment. One counted round is one fixer pass plus one fresh re-test. Three counted rounds are one epoch.

How the pieces fit

  • Progress. An epoch made progress only if fewer suites fail and fewer blocking findings remain than at its start. Failure and patch fingerprints detect a repeated failure or a repeated patch; either forces a different strategy next epoch.
  • Strict vs best effort. adversarial_best_effort_merge is off by default and never inferred. Strict never merges known failures and never becomes AI Needs Input just because findings remain. Best effort stops after the first epoch and delivers the latest commit labelled Best-effort merge with unresolved adversarial results, with the unresolved notes filed as a follow-up issue.
  • Stop conditions are the only way out of strict mode besides a clean verdict. A held issue is parked and the queue continues; a newer worker build or a removed Automation Failed label releases it with a fresh budget.
  • Quota. Any phase can pause for usage (exit 11). The session, phase, round and epoch are checkpointed and resume exactly there.

6. What happens to a finding

The tester or reviewer returns findings in two buckets.

Details

  • A finding may cite out-of-scope suite_ids. After its follow-up issue is filed (or found as a duplicate) those suites stay registered in .swarm/tests.json but no longer block this issue's verdict.
  • A finding that cites a suite under tests/adversarial/ is labelled adversarial-protected. Its follow-up skips implementation: a fresh tester adjudicates, because only an adjudicator may revise a protected test.
  • GitHub failures while searching, commenting or filing are logged and retried; they never abort the round. A model failure files the finding, because a duplicate costs noise while a suppressed vulnerability costs far more.
  • Filed issues and their URLs are kept in execution history so the app can show the non-blocking follow-ups.

7. Delivery

Nothing is delivered until every enabled stage is done and the worktree is clean. A completion comment must never describe a commit that was not pushed.

The order is mandatory: push, then PR, then comment and label. A failure in any delivery step raises and leaves the issue exactly as it was before the round. A reused branch name is never proof that a commit was delivered; an "already merged" shortcut must prove the specific commit is an ancestor of the merged one.

Values are checked against the code by test_worker_flow_docs.py; change both together.

MAX_CANDIDATES8open issues sent to the duplicate judge
DUPLICATE_MIN_CONFIDENCE0.7confidence needed to suppress a duplicate
DUPLICATE_MIN_CONFIDENCE_SEVERE0.9confidence needed for High and Critical findings
MAX_CONTEXT_ENTRIES5rediscovery notes kept in a tracked issue's description
MAX_OVERFLOW_ENTRIES30held-back findings kept in an overflow issue

Counting rules

  • Round 0 plus up to 3 counted rounds is the first epoch; each later epoch adds 3 counted rounds. Round numbers are cumulative; the epoch is (round - 1) // 3 + 1.
  • The first epoch's boundary logs read N of 3; later epochs append in epoch N.
  • Worst case for one stage in strict mode before a hold: 4 stalled epochs, so 12 counted rounds, fewer when progress is made, never more than 12 epochs or 8 hours.
  • Test counts in history are test files changed and suites failing. Capacity consumed is an approximate percentage-point drop in remaining quota, never tokens or dollars.

10. Comments and labels on the issue

One comment per transition, each opening with a unique HTML marker so a retry never double-posts. Every provider uses the same shape.

TransitionFunctionLabel effect
Startedpost_started_commentnone
Completed or Reworkedpost_pending_commentadds Ready For Testing
Stopped for usagepost_quota_commentnone
Resumedpost_resumed_commentnone
AI needs inputfinalize_needs_inputadds AI Needs Input, removes Ready For Testing
Question answeredfinalize_question_answernever adds Ready For Testing
Automation failedpost_automation_failureadds Automation Failed
Routed to protected-test reviewroute_protected_test_blockadds adversarial-protected

The adversarial stages are part of one work-round: one Started comment and one terminal comment, with a line per enabled stage. There are no per-round GitHub comments. Follow-up issues the stages file carry adversarial-uat or adversarial-security, and adversarial-protected when they cite a protected suite.

11. Where state lives

Under the repository's worker state directory (~/.local/state/swarm-issue-worker/<repo>/ on the desktop):

File or folderHolds
in-progress-issue.jsonthe active attempt: provider, session, routing decision, each adversarial stage's phase, round, epoch, approaches, filed and held-back findings, usage events
worker.lockthe per-repository lock
completed-issuesissue numbers already delivered
quota-paused-issues/attempts waiting for usage
parked-issues/held attempts, released by a new build or a removed label
abandoned/archived attempts for closed or unassigned issues
last-ai-output.log, last-ai-diagnostic.logthe latest AI session's output and diagnostics
../swarm-automation.sqlite3execution history: rounds, epochs, usage, filed findings

The checkpoint is what makes every pause, hold and yield resumable. It is deleted or archived when the issue finishes.
